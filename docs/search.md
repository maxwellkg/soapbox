# Search

Soapbox search is implemented as an internal library under the `Searchable` namespace in `lib/`. Models opt in by including `Searchable::Model`, then declaring searchable fields. Those declarations define search methods directly on the model class itself (for example, `Post.search_title`), so callers always search through model APIs rather than querying index infrastructure directly.

Basic search is SQL pattern matching backed by `LIKE` on the model's own table. A model declares it with `basic_search_on` (or `basic_search` for multiple fields), and the library generates methods like `search_email_address` on that model. Calls are translated into `WHERE ... LIKE '%term%'` conditions against the model table columns with SQL-like escaping, and blank terms return the unfiltered relation. This path is meant for simple identifier-style fields where substring matching is enough and index-table maintenance is unnecessary.

Full-text search is SQLite FTS5-backed search declared with `full_text_search_on` / `full_text_search`. These declarations also define methods on the model class (for example, `Post.search_title` and `Post.search_title_summary_and_content`), but full-text lookup uses a separate index model/table: `Searchable::IndexEntry` on `search_index_entries`. That table is shared by every model that declares full-text fields. Each index row is scoped by `indexable_type` and `indexable_id` (which model and record it belongs to) plus `field` (which indexed attribute produced the content). At query time, model search methods join `search_index_entries`, apply FTS `MATCH` filtering on index rows, and return model records (`Post` rows, not index rows), preserving a normal ActiveRecord query interface.

This shared-table structure is a deliberate tradeoff. Separate index tables per model, with one row per instance, can be more specialized, but the shared structure keeps adoption simple: full-text search is enabled by declaring fields on the model, without adding new tables or per-model indexing infrastructure. For small applications--which is to say most applications--the performance difference is usually negligible while the reduction in setup and maintenance complexity is meaningful.

The full-text index lifecycle is automatic. Models that declare indexed fields create and maintain a `has_many :search_index_entries` relationship to the index table. They reindex after commit on create/update when indexed content changes. On delete, index rows are removed through `dependent: :delete_all` on that association instead of running a reindex callback. Operationally, all indexed models can be rebuilt with `bin/rake search:reindex_all`, which calls `Searchable.reindex_all!`.

In the current application, `Post` uses full-text search for `title`, `summary`, and `content`. `Subscriber` uses basic search for `email_address` directly on the model. That split is intentional: post content benefits from full-text semantics, while subscriber email lookup is better served by simple pattern search.
